# Plan: 基于 eiCode 的多费用类型路由架构

## TL;DR

当前项目三大块（数据准备→规则引擎→回写）已通过 `ExpenseProfile` 机制做了较好的解耦，telecom 已完成 Profile 化。但**缺少基于 eiCode 的自动路由**——费用类型靠 `--profile` CLI 手动指定，`get_profile` 是硬编码 if-else，单队列混跑场景下无法按单据动态选择 profile 和图。

本方案在现有 Profile 机制基础上，新增 **eiCode→Profile 路由层**，将"先 fetch audit_info 拿到 eiCode → 再路由到对应 profile → 用该 profile 的 enricher/图/回写策略处理"这一链路打通。核心改动集中在 `application.py`（编排层增加路由分发）和 `profiles/__init__.py`（注册表改为字典 + eiCode 映射），底座 `core.py` 几乎不动。

---

## 现状分析

### 三大块现状

| 阶段 | 核心类/文件 | 现状 |
|------|------------|------|
| **① 数据准备** | `ReceiptDataPreparer`(`core.py:290`) + `ExpenseProfile.receipt_enrichers` | 底座已去 telecom 硬编码，通用 fetch 8 个 + profile enricher 插槽。telecom 已实现，travel/entertainment 未实现 |
| **② 规则引擎** | `graph_runtime/` + `resources/graphs/graph-latest-*.json` | zen-engine 执行，图按文件路径加载。3 种费用类型的图 JSON 已存在，但选择靠 `--graph-path` 手动指定 |
| **③ 回写** | `writeback.py:assemble_result_audit_info` + `ExpenseProfile` 策略包 | 通用字段组装器 + profile 注入 `compliance_rule`/`audit_travels_builder`。telecom 已实现 |

### 关键时序约束（决定架构）

**eiCode 来自 `auditInfo`，而 `auditInfo` 是 `prepare_receipt_context` 中第一个 fetch 的**（`core.py:329`）。这意味着：
- 路由无法在数据准备**之前**完成（那时还没有 eiCode）
- 路由必须在 fetch audit_info **之后**、profile enricher 注入**之前**完成
- 当前 `ReceiptAuditService` 在构造时就绑定了单一 profile（`bootstrap.py:57`），无法按单据切换

### 现存扩展性问题清单

1. **无 eiCode 路由**：`get_profile`(`profiles/__init__.py:56`) 硬编码 if-else，无 eiCode→profile 映射
2. **单 profile 绑定**：`create_receipt_audit_service`(`bootstrap.py:57`) 构造时注入单一 profile，`ReceiptAuditService` 全生命周期用一个 profile
3. **图路径硬编码**：`DEFAULT_GRAPH_PATH` 在 `runtime_client.py:11` 和 `graph_runtime/core.py:13` 两处硬编码 telecom 图
4. **CLI 默认 telecom**：`rabbitmq_worker.py:769`、`execute_graph.py:166`、`prepare_from_queue.py:157` 三处
5. **travel/entertainment profile 未实现**：`profiles/travel/` 全是 `NotImplementedError`，entertainment 无 profile 目录
6. **`context.employee` 硬编码**（`core.py:273`）：`{"name":"张三","department":"销售部","level":"P3"}` 假数据

---

## 设计方案

### 核心思路：路由分发器 + Profile 注册表

引入一个 **ProfileResolver**（eiCode→Profile 解析器），在 `ReceiptAuditService.prepare_receipt` 内部、fetch audit_info 之后调用，动态选择该单据对应的 profile。Profile 注册表从硬编码 if-else 改为字典注册 + eiCode 映射表。

```
RabbitMQ 消息 (receiptCode)
  ↓
ReceiptAuditService.prepare_receipt(receipt_code)
  ↓
  ├─ 1. fetch audit_info（通用，所有费用类型都要）  ← 拿到 eiCode
  ├─ 2. ProfileResolver.resolve(eiCode) → ExpenseProfile  ← ★新增路由
  ├─ 3. 用该 profile 的 enricher 继续准备数据
  ├─ 4. 用该 profile 的 graph_path 执行规则图
  └─ 5. 用该 profile 的回写策略包组装回写
```

### 数据流变化

**改动前**（单 profile 绑定）：
```
bootstrap 构造 ReceiptAuditService(profile=telecom)
  → 所有单据都用 telecom 的 enricher/图/回写
```

**改动后**（按单据路由）：
```
bootstrap 构造 ReceiptAuditService(profile_resolver)
  → 每单据 fetch audit_info 后，resolver 按 eiCode 选 profile
  → 该单据用选中 profile 的 enricher/图/回写
```

## Steps

### Phase 1: Profile 注册表改造（基础设施）

**1.1 新建 eiCode 映射配置文件** `expense_audit_orchestrator/profiles/ei_code_map.json`
- 结构：`{"EI001": "telecom", "EI002": "travel", "EI003": "entertainment", ...}`
- 1:1 映射（用户确认），本地维护
- 启动时加载，支持 env `EI_CODE_MAP_PATH` 覆盖路径

**1.2 改造 `profiles/__init__.py` 的 `get_profile`**
- 从硬编码 if-else 改为 **字典注册表** `_PROFILE_REGISTRY: dict[str, Callable[[], ExpenseProfile]]`
- 每个 profile 一个 builder 函数（懒加载，首次调用时构建并缓存）
- 新增 `register_profile(name, builder)` 函数供 profile 模块自注册
- `get_profile(name)` 从注册表取 builder，未命中抛 `UnknownProfileError`
- telecom 注册保留单例缓存逻辑

**1.3 新增 `ProfileResolver` 类**（放 `profiles/__init__.py` 或新建 `profiles/resolver.py`）
- `__init__(ei_code_map: dict[str, str])`：接收 eiCode→profile_name 映射
- `resolve(ei_code: str) -> ExpenseProfile`：查映射表 → `get_profile(profile_name)`
- eiCode 未命中时抛 `UnknownExpenseTypeError`（供上层捕获后标记失败）
- 支持从 JSON 文件加载：`ProfileResolver.from_map_file(path)`

**1.4 新增 `create_profile_resolver_from_env()`** 工厂函数
- 读 `EI_CODE_MAP_PATH` env（默认包内 `profiles/ei_code_map.json`）
- 返回 `ProfileResolver` 实例

*依赖：无，可独立开发*

### Phase 2: 编排层接入路由（核心改动）

**2.1 改造 `ReceiptAuditService`（`application.py`）支持动态 profile**

当前 `__init__` 接收单一 `graph_path`/`graph_content`。改为支持两种模式：
- **静态模式**（向后兼容）：传 `profile: ExpenseProfile` 或 `graph_path`，全单据用同一套（现有行为不变）
- **动态模式**（新增）：传 `profile_resolver: ProfileResolver`，每单据按 eiCode 路由

关键改动点：
- `__init__` 新增可选参数 `profile_resolver: ProfileResolver | None = None`
- `prepare_receipt`：若 `profile_resolver` 非空，先单独 fetch `audit_info` 拿 eiCode → `resolver.resolve(eiCode)` 得到 profile → 用该 profile 的 enricher 重新装配 `data_preparer` 的 `receipt_enrichers` → 继续准备
- `process_prepared_receipt`：从 `prepared_receipt` 中取出该单据选中的 `profile`（含 `default_graph_path`），传给 `graph_runtime_client.evaluate` 的 `graphPath`

**2.2 改造 `ReceiptDataPreparer`（`core.py`）支持 enricher 热替换**

当前 `receipt_enrichers` 在构造时固定。改为：
- 新增方法 `with_receipt_enrichers(enrichers: Mapping) -> ReceiptDataPreparer`：返回带新 enricher 的副本（dataclass `replace`）
- 或：`prepare_receipt_context` 新增可选参数 `receipt_enrichers_override`，传入时临时用该 enricher
- 推荐后者（避免 dataclass 复制的 slots 限制问题）

**2.3 改造 `bootstrap.py` 的 `create_receipt_audit_service`**
- 新增参数 `profile_resolver: ProfileResolver | None = None`
- 若传入 resolver：构造 `ReceiptAuditService` 时传 `profile_resolver`，不再传固定 `profile`/`graph_path`
- 若未传入：保持现有行为（向后兼容，CLI 单 profile 模式仍可用）

*依赖：Phase 1 完成*

### Phase 3: Worker 接入路由（生产链路）

**3.1 改造 `rabbitmq_worker.py`**
- `create_worker` 新增参数 `profile_resolver`，透传给 `create_receipt_audit_service`
- CLI 新增 `--ei-code-map-path` 参数（指向 ei_code_map.json）
- CLI `--profile` 保留但改为可选：传了 `--profile` 走静态模式，传了 `--ei-code-map-path` 走动态路由模式，两者互斥
- `handle_delivery` 中捕获 `UnknownExpenseTypeError`：调 `update_audit_task_status(new_status=2, fail_reason="未知费用类型 eiCode=xxx")` + `basic_nack(requeue=False)`（用户确认：拒绝并标记失败）

**3.2 改造 `execute_graph.py` 和 `prepare_from_queue.py`**
- 同样新增 `--ei-code-map-path`，支持动态路由模式
- 保留 `--profile` 用于单类型调试

*依赖：Phase 2 完成*

### Phase 4: travel / entertainment profile 落地（按需）

**4.1 实现 travel profile**（`profiles/travel/`）
- `data.py`：`travel_receipt_enricher`（行程在线 fetch + 里程标准离线资产）
- `writeback.py`：`travel_compliance_rule` + `travel_audit_travels_builder`（从 serviceData 取行程填 `auditTravels`）
- 在 `profiles/__init__.py` 注册表注册

**4.2 实现 entertainment profile**（新建 `profiles/entertainment/`）
- `data.py`：若有专属数据则 enricher，否则空 enricher
- `writeback.py`：`entertainment_compliance_rule`
- 注册表注册

**4.3 在 `ei_code_map.json` 中补充映射**
- 将实际 eiCode 与 profile 对应关系填入

*依赖：Phase 1-3 完成；可与 Phase 5 并行*

### Phase 5: 清理硬编码与测试

**5.1 清理 `DEFAULT_GRAPH_PATH` 硬编码**
- `runtime_client.py:11` 和 `graph_runtime/core.py:13` 的默认值保留作为最终 fallback，但生产链路应通过 profile.default_graph_path 指定
- 各 profile 的 `default_graph_path` 指向各自图文件

**5.2 清理 `context.employee` 硬编码**（`core.py:273`）
- 从 `auditInfo` 中提取员工信息（verifiUserName 等），无法获取时降级为空 dict 而非假数据

**5.3 补充测试**
- `tests/unit/test_profiles.py`：新增 `ProfileResolver` 单元测试（命中/未命中/空 eiCode）
- `tests/unit/test_main.py`：新增动态路由集成测试（mock audit_info 返回不同 eiCode，验证选不同 profile/图）
- `tests/unit/test_rabbitmq_worker.py`：新增未知 eiCode 标记失败路径测试

## Decisions

- **eiCode→Profile 1:1 映射**，本地 JSON 配置表维护（用户确认）。不调上游接口，避免路由依赖外部服务可用性
- **单队列混跑 + eiCode 路由**（用户确认）。路由逻辑在 `ReceiptAuditService.prepare_receipt` 内部，fetch audit_info 之后
- **未知 eiCode 拒绝并标记失败**（用户确认）。`UnknownExpenseTypeError` → `update_audit_task_status(status=2)` + nack(requeue=False)
- **目录+注册机制**（用户确认）。每个费用类型一个 profile 目录（data.py + writeback.py），通过注册表注册，核心代码不改
- **向后兼容**：保留 `--profile` 静态模式，与 `--ei-code-map-path` 动态模式互斥。现有 telecom 单 profile 部署不受影响
- **路由时序**：eiCode 来自 audit_info（第一个 fetch），路由在 `prepare_receipt_context` 内部 enricher 注入前完成。不提前路由（无数据基础）
- **图选择**：每个 profile 的 `default_graph_path` 指向各自图 JSON，`process_prepared_receipt` 按单据选中的 profile 取图路径

## Further Considerations

1. **audit_info 重复 fetch 问题**：路由需要先 fetch audit_info 拿 eiCode，而 `prepare_receipt_context` 内部也会 fetch audit_info。建议将 audit_info fetch 提前到路由阶段，结果传入 `prepare_receipt_context` 复用（加可选参数 `audit_info_override`），避免重复请求。推荐这样做——省一次 HTTP 调用且时序更清晰。

2. **profile 缓存策略**：`ProfileResolver.resolve` 每单据都调 `get_profile`，telecom 已有单例缓存。travel/entertainment 的 enricher 若含离线资产加载（如 travel 里程表），也应在 profile builder 中启动加载一次并缓存，避免每单据重读。推荐沿用 telecom 的闭包缓存模式。

3. **动态模式下的图加载**：`graph_runtime` 服务按 `graphPath` 加载图文件并缓存（`core.py:load_decision` 按 mtime 失效）。动态路由下多个单据用不同图路径，graph_runtime 的 LRU 缓存（上限 32）需确认能容纳所有费用类型的图。当前 3 种费用类型远低于 32，无风险；但若未来费用类型超 30 种需关注。推荐暂不处理，监控缓存命中率即可。
